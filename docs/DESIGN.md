# dyn-drvs: Architecture and Design

## 1. What this is, and for whom

dyn-drvs is a Nix library for building fine-grained, incremental build graphs (think: per-translation-unit C/C++ compilation) on top of Nix's dynamic-derivations feature, so that changing one source file rebuilds one derivation instead of re-running an entire package's `buildPhase`. The problem it solves: ordinary Nix derivations are all-or-nothing — a single-character change to one `.c` file invalidates the whole package derivation, and Nix has no built-in notion of "rebuild only the parts of this build that actually changed." Nix's `dynamic-derivations`/`ca-derivations` experimental features make it possible for a running build to register and submit *new* derivations on the fly (`builtins.outputOf`, `nix derivation add`, `nix store submit-output`), which means a build script can decompose its own work into a graph of sub-derivations at build time. dyn-drvs is the plumbing that makes that decomposition practical: primitives for constructing a single dynamic derivation, a compiler for eval-time-known dependency graphs, a shim that discovers build-time-known graphs (e.g. by intercepting `cc`/`ar` invocations inside an arbitrary Makefile/cmake/meson build), and a stdenv wrapper that wires the whole thing into an ordinary nixpkgs-style package. The audience is package/build-system engineers who want Nix-native, hash-addressed incremental rebuilds without adopting a separate build cache or import-from-derivation (IFD) hack.

## 2. The core primitive: `mkDynamicDerivation`

Everything in dyn-drvs bottoms out in `nix/lib/mkDynamicDerivation.nix`, which wraps an ordinary Nix derivation whose entire job is to register and submit an *inner* dynamic derivation. It factors the problem into two halves: backend-agnostic plumbing (naming, CA/output-hash attrs, the `builtins.outputOf` unwrap, `meta`/`pname`/`version` forwarding) and a backend-specific *producer*.

The producer contract is deliberately not a real abstraction with its own constructor — it's a duck-typed attrset `{ script :: backend -> string; extraDrvArgs :: attrset; }`. `script` takes the selected backend name (`"recursive-nix"` or `"builder-rpc-v0"`) and returns the entire `buildPhase` body; `extraDrvArgs` merges into the outer derivation's attrs (`nativeBuildInputs`, `passAsFile`, etc.). Because it's just a shape, not a type, every `dyndrv.builders.*` function *and* `dyndrv.graph.compile` satisfy it interchangeably — a whole compiled multi-node graph is just as valid a `producer` argument as a single `builders.viaDerivationAdd` call. One load-bearing constraint rides along with this contract: the inner derivation the producer constructs must be named exactly `"${pname}-${version}"` (the same name the outer wrapper computes), because a CA/text-hashed derivation's output path is a function of its declared name, and Nix only checks this at realization time — get it wrong and the build fails with "derivation has incorrect output '<path>', should be '<expected>'" rather than an eval-time error.

**Two backends exist because the two Nix mechanisms have genuinely different capabilities.** `recursive-nix` (used by `builders/viaNixInstantiate.nix`) runs actual Nix commands — `nix-instantiate`, `builtins.outputOf`, `builtins.storePath` — inside the sandbox, because a recursive-nix build has a full store-DB view and can realize things mid-build. `builder-rpc-v0` (used by `builders/viaDerivationAdd.nix`) cannot: its sandbox has no store-DB view and rejects `nix-instantiate`/`outputOf`/`storePath` outright ("Operation not allowed"), so all it can do is register an already-fully-known derivation via `nix derivation add` (fed hand-built JSON) and hand off its output via `nix store submit-output`. dyn-drvs supports both because `builder-rpc-v0` is the modern, forward-looking mechanism (available on real Nix master without a patched fork) that every graph/shim layer above is built around, while `recursive-nix` remains the fallback for producers that genuinely need to *run* arbitrary Nix expressions mid-build (like `viaNixInstantiate`) or for setups predating `builder-rpc-v0`. `mkDynamicDerivation.nix` calls this out explicitly as "the one place the two backends can't be fully unified."

Backend selection is handled by `capabilities.nix`, which detects exactly one thing purely at eval time: `dynamicDerivations = builtins ? outputOf`. Everything else — whether `recursive-nix`/`builder-rpc-v0` system features are actually schedulable on the build farm — is a property checked only when Nix tries to schedule a build, so `capabilities.nix` approximates `recursiveNix` as equal to `dynamicDerivations` and hardcodes `builderRpcV0`/`submitOutput` to `false` as an intentionally conservative default (a real probe is deferred to a future `dyndrv doctor` CLI). This is a separate concern from `mkDynamicDerivation`'s own default of `backend = "builder-rpc-v0"` — a policy choice, opted out of via `backend = "auto"`, which then falls back through `capabilities.withFallback { dynamic; ifd; }`: if dynamic derivations are usable it returns the `dynamic` branch, otherwise it degrades to whatever ordinary IFD-based expression the caller supplied as `ifd`. dyn-drvs has no opinion about what that IFD path looks like — it just routes to it.

Two permanent rough edges of `builtins.outputOf` are papered over by `mkOutputOf.nix`, both confirmed by Nix's own test suite rather than being dyn-drvs bugs: `outputOf` requires a literal string (not a derivation attrset), so `mkOutputOf` extracts `drv.drvPath` itself; and `outputOf` rejects strings whose context is `DrvDeep` (the natural context of `drv.drvPath`), so `mkOutputOf` unconditionally applies `builtins.unsafeDiscardOutputDependency` (a documented no-op on already-`Opaque` strings, so it's safe to always apply). Every `mkDynamicDerivation` output exposes `passthru.dynamicDrv` (the raw outer `.drv`-producing derivation), `passthru.outputOf` (the fully resolved output, after two chained `outputOf` calls — one to resolve the outer derivation's own output to the inner `.drv`, one to resolve that `.drv`'s own output), and `passthru.backend`. The point of this uniform contract is that "I need the raw thing underneath" is always the same two attribute names, regardless of which builder or graph-compile call produced the derivation.

## 3. Composition layer 1: `graph.compile` — eval-time-known graphs

When you already know your dependency graph at eval time — a fixed set of source files with fixed dependencies — `nix/lib/graph/compile.nix` is a *producer constructor*: it returns the same `{ script, extraDrvArgs }` shape a single `viaDerivationAdd` call returns, so it plugs directly into `mkDynamicDerivation` as `producer`.

Given `nodes = { <name> = { deps, group, mkDrv }; }`, it topo-sorts the nodes (`graph/topoSort.nix`, Kahn's algorithm, throwing on cycles), buckets them into "units" (see grouping below), and topo-sorts the *unit* graph too (since grouping can put topologically distant nodes in one unit, cross-unit edges still need ordering). For each unit, in order, it emits bash that writes that unit's `drvJson`, substitutes same-unit ("self") output references with real `builtins.placeholder` values, wires every already-registered dependency unit into `inputs.drvs` by its real basename, substitutes cross-unit references with that dependency's computed `DownstreamPlaceholder`, and runs `nix derivation add` — recording the result into bash associative arrays so later units can reference it. All of this is ONE generated script, because crossing the eval→build JSON boundary per node would lose Nix's own string-context dependency tracking. The script ends with exactly one `nix store submit-output`, matching `builder-rpc-v0`'s one-output-per-derivation constraint. (`recursive-nix` codegen for this path is unimplemented — it throws.)

**Grouping.** A node is either "solo" (its own unit, output named `"out"`) or carries a `group` string; every node sharing a `group` becomes one unit — one `nix derivation add` call producing one multi-output derivation, with each member exposed as `$<memberName>` per Nix's own multi-output ABI. `groupByDirectory.nix` is sugar setting `group = lib.dirOf (pathOf name node)`, i.e. "everything in one source directory becomes one registered derivation" — a way to trade maximal per-file granularity for fewer, larger round-trips when registration overhead outweighs granularity. Mechanically, grouped members compile into one concatenated `/bin/sh -c` script in topo order; each member's `mkDrv` must return exactly `builder = "/bin/sh"; args = ["-c" "<cmd using $out>"]`, and `graph.compile` rewrites `$out` to that member's own `$<memberName>` before concatenating.

**Assembling the final output.** Since only one output can be submitted, `toOutput` decides how the graph's many node outputs become that one. The default `"assemble"` synthesizes a final node that symlinks every other node's output into `$out/<nodeName>` (a directory-tree pattern borrowed from gradle-drvs). `{ sink = "<nodeName>"; }` instead symlinks `$out` directly at one named node's output, skipping the rest. Either way the synthesized node's registered name must equal `graph.compile`'s own `name` argument, since that's what the outer `mkDynamicDerivation` wrapper expects.

**Why a placeholder is needed at all.** For a CA/dynamic derivation, a dependency's real output path is a hash of its *content*, unknowable until it's actually built — yet the depending unit's JSON has to be registered, referencing that output, before any building happens (registration proceeds unit-by-unit in topo order). Nix's own `DownstreamPlaceholder::unknownCaOutput` mechanism produces a deterministic stand-in string — purely a function of the upstream drv's hash-part and output name — that Nix transparently substitutes once the real output is realized. `graph.compile`'s `placeholderBashFn` is a verified bash port of that formula (`clearText = "nix-upstream-output:$drvHashPart:$outputPathName"`, SHA-256'd and nix32-encoded). Same-unit references use a cheaper sentinel resolved via `builtins.placeholder`, since no cross-derivation lookup is needed.

## 4. Composition layer 2: the shim — build-time-discovered graphs

`graph.compile` requires the graph shape at eval time. Real build systems (`make`, `ninja`, cmake, meson) don't expose their dependency structure until the build tool has actually walked the source tree. The shim (`nix/lib/shim/wrapCommand.nix` + `nix/lib/shim/collectStubs.nix`) solves this by intercepting `cc`/`ar`/`ranlib` invocations during an ordinary build run and reconstructing the same "unit" algorithm `graph.compile` uses, but operating on a graph discovered piecemeal at build time instead of declared up front.

**Why deferral, not immediate registration.** Nix's daemon enforces a connection-mode opcode allowlist for `builder-rpc-v0` sandboxes: only `AddToStore*`/`SubmitOutput`/`AddTempRoot`/`IsValidPath` are permitted; `BuildPaths`/`QueryMissing` are rejected. A script inside such a sandbox can register a derivation but can never realize it or block on its result mid-script. (An earlier "materialize" mode that registered-then-realized inline depended on `recursive-nix`'s different sandbox, which *can* call `BuildPaths`; once the accelerate layer moved fully onto `builder-rpc-v0`, that mode became unreachable and was removed.) So every intercepted invocation defers unconditionally: `wrapCommand.nix` writes a *stub* — a plain regular file (never a symlink, because "nothing exists yet at the eventual output for a symlink to point at, and a dangling symlink fails a plain `test -e`" that many build tools use as a freshness gate) containing a fixed header line and a pointer to a JSON record file (`shim/batchStub.nix`). Nothing resolves these stubs until `collectStubs.nix` runs once, at the end of `buildPhase`.

**Mirroring `graph.compile`'s algorithm, at build time.** `collectStubs.nix`'s own comments describe it as "a direct bash port" of `graph/compile.nix`'s unit/render algorithm, operating on bash associative arrays discovered from scattered stub records instead of an eval-time attrset. It proceeds through numbered phases: walk the build tree for stubs; compute each stub's dependencies by scanning its own recorded `args` for other stubs' relative paths (no separate schema needed, since a leaf compile has no deps and a link/archive step's positional inputs *are* its dependencies); topo-sort the whole discovered graph (Kahn's algorithm, ported to bash via namerefs); assign units (a stub with its own `key` joins that unit; a keyless stub like `ar`/`ranlib` joins its deps' shared unit only if all deps share the same non-solo unit; anything else is solo); register one `nix derivation add` per unit in unit-topo order, wiring `inputs.drvs` and substituting placeholder sentinels via a bash function copied verbatim from `graph/compile.nix`'s `placeholderBashFn`, "so the two can't silently drift apart"; and build a final node that overlays resolved outputs onto the *original* build tree's directory structure (replacing each stub path with a symlink) rather than a flat assembly directory, because `phases/split.nix`'s subsequent `installPhase` expects a normal build-tree layout.

Getting this dependency-matching right required a specific fix: a build step's cwd can differ from the cwd of the invocation that produced one of its inputs (cmake's `cd build && cc ... -o exe` referencing a `.o` produced from a different working directory), which otherwise makes the same file two different relative-path strings. Each stub now records `cwd` relative to `NIX_BUILD_TOP`, and `dyndrv_join_rel`/`dyndrv_relative_between` reconcile it against the shared build-root frame before matching — a normalization step needed even in the *non-mismatched* case, since an ordinary compile still has a non-empty `record.cwd` that would otherwise corrupt every join. A related mechanism, `chainedFrom`, handles two deferred invocations landing on the identical output path in sequence (`ar cr lib.a *.o` followed by `ranlib lib.a`): rather than the second stub silently overwriting the first's record (and with it, its dependency on every `.o`), `wrapCommand.nix` chains the pointer back so `collectStubs` unions both steps' dependencies and renders them as a sequential command.

Outside the sandbox — in `shim/devShell.nix`, used for interactive `nix develop` sessions — the same interception logic runs against an unrestricted daemon connection (no opcode allowlist applies outside a sandboxed build), so it registers real derivations directly instead of deferring via stubs, and can even eagerly realize the whole graph. This works only because a shared `Record`→`Derivation` translation path guarantees a translation unit registered by hand in the dev shell lands at the identical content-addressed store path as the same TU registered inside a real sandboxed build — so Nix substitutes rather than rebuilds.

## 5. Composition layer 3: `accelerate.mkAcceleratedStdenv` + `phases.split`

This is the layer that makes the shim usable as a drop-in `stdenv` replacement for an arbitrary nixpkgs-style package. The core tension: `buildPhase` needs to run under `builder-rpc-v0` (to defer/register compiles), but `installPhase`/`fixupPhase` need a real, already-resolved `$out` tree to copy into, fix RPATHs against, and split into multi-output paths — exactly the "realize a derivation for real" operation `builder-rpc-v0` sandboxes structurally cannot do inline. `nix/lib/phases/split.nix` resolves this by splitting the build into two actual derivations: phase 1 is sandboxed (`requiredSystemFeatures` includes `"builder-rpc-v0"`) and runs unpack/patch/configure/build plus a synthesized `collectPhase` that submits a fully-resolved tree; phase 2 is an ordinary derivation with no special capability that consumes phase 1's output and runs install/fixup/check normally.

Phase 1 has no real `$out` — it's forced to the literal placeholder string `dyndrvPlaceholderOut = "/build/dyndrv-placeholder-out"`. Packages whose `configureFlags` bake `$out` literally into generated build files (stdenv's multi-output machinery, e.g. `--prefix=${dyndrvPlaceholderOut}`) freeze that placeholder into the build system, so phase 2's `installPhase` writes everything under the placeholder root instead of real per-output paths. `dyndrvRestoreOutput`, inserted right after `installPhase` and before `fixupPhase`, fixes this by copying the placeholder tree's content into the real `$out` and re-invoking stdenv's own multi-output-doc/dev-splitting logic immediately, rather than relying on the ordinary hook array — because a caller's own `preFixup` hook can run first and expect `$dev/include` to already exist. The placeholder must live under `/build` specifically (not `/nonexistent`, not an env var) because the sandbox root filesystem is unwritable even to the build group, `/build` is Nix's guaranteed-writable `sandbox-build-dir`, and a literal string is required so the same value resolves identically whether baked into a Makefile in phase 1 or read back in phase 2's separate sandbox.

`mkAcceleratedStdenv` also has to reimplement nixpkgs' own `finalAttrs`/`overrideAttrs`/`makeOverridable` fixed-point pattern rather than reuse it as-is, because `phases.split`'s returned derivation is literally phase 2's derivation — its default `overrideAttrs` would reconstruct phase 2 with `src` still pointing at phase 1's stale resolved output, silently dropping any override that needs to reach `patchPhase` (which only runs in phase 1). The custom `overrideAttrs` re-runs the *whole* `phases.split` call, phase 1 included. `finalPackage` (bound to the function's own eventual return value) had to be added explicitly because real, unmodified packages like openssl read `finalAttrs.finalPackage.doCheck` at multiple call sites and eval fails outright without it.

## 6. The Rust port (dyndrv-shim)

The bash shim originally shelled out to `nix-instantiate --eval --strict --json` per intercepted invocation to run its decision logic, plus `jq` and store-add subprocesses. Direct measurement identified Nix-evaluator boot time — not `jq`'s fork+exec — as the dominant per-call cost. `dyndrv-shim`, a compiled Rust binary, replaces the entire wrapper with one exec that talks to the daemon's worker protocol directly (`nix-builder-rpc-client`), eliminating all three subprocess spawns. This is a performance optimization, not a behavior change: the on-disk stub/record format is identical, and bash and Rust producers/consumers can freely interoperate within the same build.

The Rust binary supports four `DyndrvMode` variants: `Sandbox` (inside `builder-rpc-v0`; registration-only, with eager-registration fast paths — file-granularity and module-granularity accumulation — that bypass the text-stub-and-collect flow entirely when no dependency is still a pending text stub, leaving a real symlink into the store as the pending marker instead); `Rpc { autoforce }` (devShell/native, unrestricted daemon, can realize inline); and `Thunk { format, autoforce }` (no dynamic-derivations requirement at all — writes a `.nix` expression or a real ATerm `.drv` file to a workspace-relative thunk directory, for contexts without the experimental features enabled).

Because four independent call sites construct derivation text for these modes, dyn-drvs guarantees byte-identical ATerm output between them through one shared function, `render_record_line`, that all four now delegate to instead of each hand-rolling the same construction — a bug where two call sites' hand-written copies disagreed on a trailing separator, producing different derivation hashes for the logically identical case, is what motivated unifying this into a compile-time-enforced single implementation. A `cross_mode_tests` suite asserts byte-identical output across representative `Record` shapes on every CI push, backed by real-project fixtures that confirm actual substitution events (a build whose log shows neither TU being rebuilt, with a negative control proving the check means something).

## 7. What this is NOT

dyn-drvs is not a general-purpose, drop-in accelerator for arbitrary nixpkgs packages today. Documented, currently-open gaps include: cmake-generated builds routinely fail with "source file not found" due to a still only partially-traced cmake-relative source-path resolution bug; freshly linked binaries can lose their executable bit, breaking packages that self-exec a just-built binary before `installPhase`; `phases.split` forces single-output mode without clearing an inherited `outputBin`/`outputMan`/`outputDev` override, breaking any package that sets those explicitly (e.g. libpng, libtasn1); automake's `-MF .deps/$*.Tpo` depcomp idiom breaks because only a compile's primary `-o` output round-trips out of the sandbox, not its depfile side-output (gperf and other autotools projects); `autoreconfHook`'s dynamic phase injection is silently dropped because `phases.split`'s `sandboxedPhases` is a static list, with no package-level override available (mosh); packages reading nixpkgs' `finalAttrs.finalPackage` self-reference fail at eval time unless that attribute happens to be wired in; and `discoverTree`'s dependency-scanning approach (a `cc -M -MG` header scan) structurally cannot see `.o`/`.a` positional inputs to a link step, so any `cc`/`c++`-driven link (as opposed to an `ar`-driven archive step) risks losing real dependency edges. `graph.compile` also has no `recursive-nix` codegen path at all — it only targets `builder-rpc-v0`. None of this is upstream Nix's fault: the two upstream blockers dyn-drvs tracks (`builder-rpc-v0`'s merge status, and an incomplete `outputOf` monadic-join) are both worked around already (`outputOf` chaining is hardcoded to exactly two levels, not general N-level).

## 8. When to use this

The validated sweet spot, from direct measurement against real nixpkgs packages (both in this repo's own benchmarks and an independent downstream showcase), is narrow: plain, hand-written Makefile projects with no autotools/libtool, no cmake, and no meson-generated build (giflib, tree, figlet, nnn), where individual translation units are expensive enough to compile that the fixed ~80ms `nix derivation add` registration tax per unit is negligible by comparison. The break-even point is real and measured: a near-break-even fixture crosses over around 30 files at ~280ms/compile, and freetype — this project's own flagship "it registers exactly the right derivations and rebuilds only what changed" proof point — is nonetheless a net wall-clock *loss* on cold builds (roughly 0.06x-0.35x of a plain rebuild in this repo's own numbers, independently reconfirmed at ~0.15x in the downstream showcase) because its individual compile units are too fast to amortize the tax. Every failure mode surveyed beyond the plain-Makefile case traces back to an autotools- or cmake-specific build-system idiom (depcomp side-outputs, `autoreconfHook` phase injection, cmake compiler-flag probes, cmake-relative source paths, `cc`-driven link steps) rather than anything about the target language or package size — so the honest framing is: use dyn-drvs today for small-to-medium, Makefile-only C/C++ utilities with individually nontrivial per-TU compile costs, and expect real work before it's the right tool for an autotools- or cmake-based project, or for any package where per-file compile time is measured in tens of milliseconds rather than hundreds.
